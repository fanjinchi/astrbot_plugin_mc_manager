## 0. 结论先行

- **Issue #5 最初的目标包含"来源（modid）/权限/说明"，但最终 PRD 收窄为"语法级 MVP"，明确排除了中文描述与语义映射。**
  因此"模组命令没有中文"不是实现偷懒，而是范围决策的结果——但这个决策与最初的预想有落差，值得重新摆到桌面上讨论。
- **命令名本身无法中文化**：Brigadier 的 command literal 是玩家实际输入的英文标识符，不可本地化。
  所谓"中文"只能是**描述 / 别名 / 语义层**，它不是命令语法的一部分。
- **从 dump 数据里拿不到任何中文**：`getAllUsage` 只给 usage 字符串；Brigadier 节点没有描述字段，MC 的 `/help` 也不输出说明。
  要做中文，必须引入**dump 之外的信息源**（人工字典 / 离线 LLM 生成 / 文档语料），这是一个独立的需求决策。

## 1. 现在实际实现到什么程度

### 1.1 数据产物（`<mc_server_dir>/runtime_dump/commands.json`）

```json
{"kind":"commands","schema_version":1,"producer":"kubejs","count":2,
 "entries":[
   {"name":"wine","syntax":"wine age <years>","source":"unknown","level":null},
   {"name":"wine","syntax":"wine info","source":"unknown","level":null}
 ]}
```

| 字段 | 含义 | 模组命令的真实取值 |
|---|---|---|
| `name` | 根 literal（英文，玩家必须原样输入） | 如 `wine`、`ae2`、`kubejs` |
| `syntax` | 一条完整 usage 路径 | 英文 + `<参数名>` |
| `source` | 来源标记 | 固定 `unknown`（无法可靠推断 modid） |
| `level` | 游戏内权限等级 | 固定 `null`（Brigadier 不暴露数值等级） |
| `redirect` | 别名/重定向目标（可选） | 如 `alias -> foo`、`loop ...` |
| `desc` | 中文描述 | **不存在**（契约允许缺省，本期不生成） |

### 1.2 查询侧体验

- 原版命令：能显示内置中文描述（来自 `assets/vanilla_commands.json`，74 条），中文关键词可搜。
- 模组命令：只有 `- /wine — 运行时命令（来源未知，权限未知）` + 英文 usage 列表。
- 中文搜模组：`search("葡萄酒")` → 未找到（库里没有这个字符串）。

### 1.3 相关但独立的问题（已列入本轮修复，不影响本次讨论）

- **P0**：快照存在后，原版命令的中文描述搜索失效（合并同根时 desc 只用于显示、没参与匹配）。修复后原版中文搜索恢复。
- 无结果文案在快照已存在时仍提示"模组命令需服务器侧导出"，误导。

## 3. 为什么"中文"不是顺手能加上的（技术事实）

1. **Brigadier 节点没有描述字段**。`CommandNode` 只有 name / usage / children / redirect / requirement / command。
2. **`/help` 不输出说明**。原版 help 走 `getSmartUsage`，只有命令与参数结构；模组自定义 help 也不保证有。
3. **语言文件不覆盖命令**。模组 `zh_cn.json` 覆盖物品/方块/进度/书页，**没有命令名或命令描述的键**；而且命令 literal 是玩家输入的标识符，本质不可本地化。
4. **modid 归属不可靠**。dispatcher 节点不带注册者信息；按命令名前缀猜 modid（`ae2` → AppliedEnergistics）会造假数据。
5. **权限等级不可靠**。`requires` 是 `Predicate<CommandSourceStack>`，没有可读数值；强行用合成 source 探测 0–4 级风险高且结果不准。
6. **玩家可见 ≠ RCON 可见**。导出用的是 `restricted=false` 全树，含玩家限定/高权限命令，不代表当前调用者能执行。

→ 结论：中文**必须来自外部信息源**，而且只能是"描述/别名"，不能是"精确翻译"。

## 4. 影响评估：没有中文会怎样

| 场景 | 现状 | 后果 |
|---|---|---|
| 用户/LLM 说"查一下 TPS" | 搜"TPS" 可能命中 `forge tps`（英文词偶然相同） | 看运气 |
| 用户说"用 葡萄酒 那个查年份" | 搜不到 | LLM 只能瞎猜或放弃 |
| LLM 已知 mod 英文名（`wine`） | 能查到 `wine age <years>` | 可用 |
| 整合包服主熟悉 modpack | 能自己给出英文命令 | 可用 |
| 整合包有中文任务/手册文档 | 目前无检索（依赖未立项的 #3） | 中文玩家体验断层 |

现实判断：**语法级 MVP 对"LLM 已经知道模组英文名"的场景够用，对"中文玩家只说功能"的场景不够用。** 这正是要讨论的需求边界。

## 5. 可选路线（供 grill 取舍，尚未评估完）

### A. 服主维护的中文字典（最小可落地）

数据形态（新增文件，例如 `<data_dir>/commands_zh.json`）：

```json
{
  "wine": {"desc": "葡萄酒酿造年份查询", "aliases": ["葡萄酒", "年份", "酿酒"]},
  "ae2":  {"desc": "应用能源2 网络与终端", "aliases": ["AE", "线缆", "终端"]}
}
```

- 查询时把 `desc`/`aliases` 并入匹配与展示，标记来源为"人工补充"。
- 成本：低；风险：覆盖率取决于服主投入；不随 dump 自动更新。
- 可复用的既有模式：`zh_cn_extra.json`（物品自定义中文名）已经是同款思路。

### B. dump 后离线 LLM 生成描述 + 审核入库

- 输入 `commands.json` → LLM 批量生成 `{name, desc_zh, aliases}` → 人工审核 → 派生库。
- 成本：高（生成 + 审核 + 版本漂移）；风险：幻觉、错误归类，必须带"未审核/推测"标记。
- 需要定义：刷新策略（dump 变化后增量更新）、审核记录、回滚。

### C. 靠文档 RAG 间接覆盖（Issue #3 轴）

- 用 CFPA 指南 / Patchouli 手册 / FTB Quests 任务文本做检索，回答"这个 mod 怎么用"。
- 风险：返回的是文档片段，不是命令映射；与 #3 的范围强耦合；#3 自身尚未 grill。
- 价值：对"XX mod 的 YY 功能"这类自然语言问题最自然。

### D. 混合（推荐作为讨论起点）

- A 的字典作为**确定信息层**（人工/服主维护、零推断）；
- 无结果时明确提示"模组命令只有英文根名与参数语法，请用英文/参数词重试"（文案级，1–2 行）；
- B 的生成结果只作为**候选提示**（默认不进主查询，或明确标注"未审核"）；
- C 留给 #3，不与命令库耦合。

### 方案对比

| | 覆盖率 | 维护成本 | 事实风险 | 与现有代码耦合 | 能否离线 |
|---|---|---|---|---|---|
| A 人工字典 | 低→中（靠人） | 低 | 极低（人写的） | 很小（新增可选文件+查询合并） | 是 |
| B LLM 生成 | 高 | 高（审核） | 中（幻觉） | 中（新增生成/缓存流程） | 生成需模型；查询可离线 |
| C 文档 RAG | 中→高（看语料） | 中 | 中（答非所问） | 大（独立子系统） | 是（若本地检索） |
| D 混合 | 中 | 低→中 | 低 | 小 | 是 |

## 6. 必须拍板的决策点（grill 清单）

1. **目标用户**：服主 / 普通玩家 / LLM 自己用？三者的中文需求不同。
2. **覆盖面**：只做高频 top-N，还是要求"任意模组命令都能用中文找到"？
3. **中文来源优先级**：人工字典 / LLM 生成 / 文档抽取 / 混合？是否允许"推测"进入结果？
4. **是否需要 modid 与模组中文名归属**？精度要求是什么（准确 vs 大概）？
5. **是否需要权限等级**？不可得时接受"未知"，还是要做探测（成本高）？
6. **数据归属**：派生缓存（可重建、随 dump 变）还是手工配置（不被覆盖）？两者如何叠加与排序？
7. **维护者与频率**：谁来补字典？多久更新一次？升级 modpack 后旧条目怎么办？
8. **审核要求**：LLM 生成的内容是否必须人工过目？审核记录要不要留？
9. **失败与漂移**：新命令无描述怎么显示？命令被删/改名后旧描述怎么清理？
10. **离线要求**：无网络、无模型 key 的服务器上，最低可用形态是什么？
11. **验收口径**：用"中文关键词命中率"、"LLM 选对命令的比例"，还是"玩家任务成功率"衡量？如何取样？
12. **范围边界**：是否与 #3（文档问答）、#1（配方）共用一套"模组语义"设施，还是各做各的？

## 7. 如果立项，改动面有多大（现状契约的可扩展点）

- 快照契约：`validate_snapshot` 目前**只保留白名单字段**（name/syntax/source/level/redirect），额外字段会被丢弃。
  若要中文描述进入快照，需要放宽校验；更推荐**不要动快照契约**，中文层作为独立可选数据源（人工字典或派生库）在查询侧合并。
- 查询侧已有挂载点：`_merge_with_vanilla`（同根继承 desc/cat）与 `_format_runtime`（无描述时显示占位"运行时命令"）。
  中文层只需在这里补充 desc 来源并参与打分。
- 发布/失败关闭/原子替换一套机制可直接复用（`kb/commands.py`）。
- 需要新增：中文数据源的校验/发布/优先级/冲突处理；以及"描述来自哪里"的标注（人工 / 生成 / 文档）。

## 8. 明确的非目标（建议写进新 PRD 的 Out of Scope）

- 不把命令名翻译成中文（literal 必须保持英文，否则玩家无法输入）。
- 不从 JAR 静态扫描或日志猜测命令（命令是运行时注册的）。
- 不伪造 modid、权限等级、参数可选性/类型/范围。
- 不在每次 `execute_command` 前全量扫描服务器。
- 不把未审核的 LLM 生成描述当作事实展示（除非明确标注）。
- 不要求本期同时覆盖"命令中文"与"文档问答"两条轴（后者是 #3）。

## 9. 验收标准草稿（可测，供 PRD 改写）

- [ ] 给定一份包含 N 个模组根命令的快照 + 一个中文关键词表，查询能在 top-K 内命中正确命令，命中率 ≥ 约定阈值（阈值需 grill 决定）。
- [ ] 未配置中文数据源时，行为与本期语法级 MVP 完全一致（不回归）。
- [ ] 中文数据源损坏/缺失时，查询降级为英文搜索并给出明确提示，不把错误文本当数据。
- [ ] 每条中文描述都能标注来源（人工/生成/文档），不出现无来源的"猜测即事实"。
- [ ] 原版命令的中文描述搜索保持可用（P0 修复后的既有能力，不得回退）。
- [ ] 文档说明中文层的配置方法、覆盖率口径、限制与升级维护流程。

## 11. 建议的讨论顺序

1. 先确认"中文"要解决的是**谁的什么痛点**（Q1/Q2），再谈实现。
2. 用方案 A 的最小形态做一次成本/收益判断（服主愿意维护多少条？）。
3. 若要求"任意模组命令都能中文找到"，直接进入 B（生成+审核）的成本讨论，并确认幻觉治理责任。
4. C 明确交给 #3，只讨论接口边界（命令库是否提供"命令 → 文档锚点"）。
5. 最后写非目标与可测验收标准，避免再次出现"预期包含中文、PRD 排除中文"的落差。
